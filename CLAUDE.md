# rechtzeitig

GitHub Action that scans a website and its repository for German legal basics, security and an SBOM. Read README.md, then dev/architecture.md.

## Where things live

| What | File |
|---|---|
| One rule | `checks/<module>/<name>/`: `rule.yml` (metadata), `check.ts` (detection), `test.ts`, `fixtures/` |
| User docs | The [wiki](https://github.com/kreativ-anders/rechtzeitig/wiki), cloned into `wiki/` by `npm run docs`. Pages `Inputs`, `Checks` and `Checks-<Group>` are generated from `action.yml` and `rule.yml` (`src/docs.ts`) and pushed by the release workflow; the others are edited in the wiki by hand. rechtzeitig.dev shows the wiki through the dashboard |
| Words per language (detection patterns); English report messages | `lang/*.yml`; messages only in `lang/en.yml` |
| Known services, countries, cookies | `data/third-parties.yml` |
| Paths requested without a browser | `data/probes.yml` |
| Secret patterns | `data/secrets.yml` |
| License groups, update tools | `data/licenses.yml`, `data/update-tools.yml` |
| Lists for single checks (countries, cookie names, error traces, closed services) | `data/*.yml` |
| Thresholds and list caps of all checks | `data/thresholds.yml` |
| Lockfile parsers | `src/repo/lockfiles.ts` |
| Package files without a parser, registries, ecosystems with license data | `data/ecosystems.yml` |
| Allowed source domains for `meta.sources` | `data/source-domains.yml` |
| Public Suffix List (what counts as one site), MPL-2.0 | `data/public-suffixes.dat`, refreshed with `npm run refresh-suffixes` |
| Periodic review of rule sources | `.claude/skills/review-sources/` |
| Check that rule docs and sources match the code | `.claude/skills/check-rule-docs/` |
| Inputs of the action | `action.yml` (its descriptions become the wiki page `Inputs`); command line options in `src/options.ts`; set in the example or commented in `FILE_ONLY` of `src/inputs.test.ts` |
| Turning rules off (`.github/rechtzeitig.yml` of the scanned repository) | `src/suppress.ts`, rule `checks/quality/suppressions/`, template `examples/rechtzeitig.yml` and schema `examples/rechtzeitig.schema.json` (both generated by `npm run docs`) |
| Releases | `.github/workflows/release.yml`, started by hand with patch, minor or major |

## Keep the documentation true

Every change that affects what a rule does updates its documentation in the same commit:

- Detection changed in `check.ts` → update `how` in `rule.yml` (one sentence, names the data files used).
- Legal basis, wording or threshold changed → update `legal_basis`, `fix_hint`, `meta.sources`, and set `meta.last_reviewed` to today.
- Rule added, removed or renamed → `rule.yml` with a new unique id, then `npm run docs`. It also writes the rule into the list in `examples/rechtzeitig.yml` and into `examples/rechtzeitig.schema.json`; tests fail until both are current. The wiki gets it with the next release. A renamed id breaks users' `.github/rechtzeitig.yml` entries (`unknown_rule`): say so in the commit message.
- Data file changed in a way that changes results (new vendor, pattern, probe) → mention it in the commit message.
- Input added or changed → `action.yml`, `src/options.ts`, `examples/workflows/rechtzeitig.yml` (set in `with:`, or commented with its default and named in `FILE_ONLY` in `src/inputs.test.ts`), `.github/workflows/rechtzeitig.yml` if this repository needs it. An input that sends data also goes into the wiki pages `Data-and-safety` and `Getting-started`.
- Architecture changed → `dev/architecture.md`.

If a commit changes `check.ts`, a rule's messages in `lang/` or a data file and nothing in the docs needs to change, say why in a line `Docs-unchanged: <reason>`. `npm run drift` (also in CI) fails otherwise; a changed data file can instead be named in the message.

A change that the hand-written wiki pages describe (report, suppressions, data that leaves the runner, setup) is edited in the wiki when the PR is merged; the wiki shows released behavior, so prefer editing it with the release.

Then run `npm run docs && npm run typecheck && npm test`. Tests fail when `examples/rechtzeitig.schema.json` or the rule list in `examples/rechtzeitig.yml` is stale, a link between wiki pages breaks, a rule is invalid, has no source, is older than a year, or its `how` misses a data file its `check.ts` loads. For what tests cannot judge, use the `check-rule-docs` skill.

## Boundaries

- Words belong in `lang/*.yml`, services and patterns in `data/`, numbers a check decides by in `data/thresholds.yml`, never in check code.
- No paid features or paid code paths in this repository.
- Findings are technical risk hints with location and legal basis, never legal advice.
- No exceptions for this repository: no path, pattern, threshold or marker exists to make rechtzeitig's own scan pass; tune against external code and fixtures, and report what rechtzeitig finds on itself.
- A check that asks an outside service only uses that service's official API, and is always opt-in: with a token it runs only when the user sets the secret, without a token only when the user sets its input to `true`. Nothing about the scanned project leaves the runner by default (enterprise security reviews treat every outside connection as critical). The example workflow sets each such input to `"false"` with a comment saying what it sends, so the choice is visible. Documented in the wiki pages `Data-and-safety` (a test fails when a service is missing) and `Getting-started`; `Inputs` lists it from `action.yml`. Both kinds are listed in `SWITCHES` in `src/rules.ts` and named in the rule's `requires`; `src/inputs.test.ts` fails when one is on by default. No unofficial endpoints, no scraping, no fallback that sends data without a token.
- Commercialization plans go into the section "Commercialization" of `dev/roadmap.md`, nowhere else. No prices or competitor names.
- Docs are English only, short and plain, to keep maintenance and translation at zero. The wiki is for users, `dev/` for contributors.
