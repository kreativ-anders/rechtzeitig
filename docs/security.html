Security headers, TLS and exposed files, checked in CI

rechtzeitig is a GitHub Action that checks your site's security headers, HTTPS and TLS certificate expiry, SPF and DMARC, and looks for exposed .env and .git files on every run. No API key and no account: these checks talk only to your site and its DNS.

What is checked

These are the website checks of the security group. Each links to its card on the checks page with its sources. The list is generated from the rules, so it matches what runs. Committed secrets and open database rules are checked in the repository group.

  • Cookies use secure flags

    SEC-HDR-002 · Art. 32 GDPR

    How it is checked Checks Secure on every cookie set without login (HTTPS sites, and always with SameSite=None) and HttpOnly on cookies whose name looks like a session (data/cookies.yml); cookies of other sites only give info.

    Fix Set cookies with Secure; session cookies also with HttpOnly and SameSite=Lax.

  • CORS does not share answers with credentials to any site

    SEC-HDR-005 · Art. 32 GDPR

    How it is checked Reads the response headers of the site's own pages and fails when Access-Control-Allow-Credentials: true comes with Access-Control-Allow-Origin * or null; it sends no foreign Origin, so a server that mirrors any Origin is not detected.

    Fix Send Access-Control-Allow-Credentials only with a fixed list of trusted origins, never with * or null, and do not copy the Origin from the request unchecked. If the pages need no CORS, leave out both headers.

  • Domain is protected against email spoofing

    SEC-DNS-001 · Art. 32 GDPR

    How it is checked Reads the SPF TXT record of the registrable domain and the DMARC record at _dmarc.; flags missing ones, SPF that allows every server (+all, ?all) and DMARC p=none.

    Fix Publish SPF and DMARC records; a domain without mail needs only "v=spf1 -all" and "v=DMARC1; p=reject".

  • Error pages reveal no internals

    SEC-EXP-002 · Art. 32 GDPR

    How it is checked Requests the paths from data/probes.yml, searches the visible text of the error paths for the traces in data/leaks.yml, and the headers of the start page and every probed path for the version headers in data/leaks.yml (server only with a version number).

    Fix Turn off error output in production (for example display_errors=0, DEBUG=false) and remove version headers.

  • No private files are public

    SEC-EXP-001 · Art. 32 GDPR

    How it is checked Requests the file paths from data/probes.yml; a 200 whose body matches expect fails.

    Fix Remove the files from the web server or block access to dot files and backups; change any credentials they contain.

  • Security headers are set

    SEC-HDR-001 · Art. 32 GDPR

    How it is checked Reads the response headers of the start page (HSTS, CSP, X-Content-Type-Options, Referrer-Policy, frame protection), accepts CSP and Referrer-Policy from <meta> tags, which browsers apply too, and HSTS as given for top-level domains in data/hsts-preload.yml.

    Fix Set the missing headers in the web server or hosting. CSP and Referrer-Policy also work as <meta> tags; frame-ancestors and nosniff only work as headers.

  • www and non-www addresses both work

    SEC-DNS-002 · Art. 32 GDPR

    How it is checked Requests the domain with www. added or removed and follows redirects.

    Fix Get a valid certificate for both addresses and redirect one to the other.

  • Site uses HTTPS

    SEC-TLS-001 · Art. 32 GDPR

    How it is checked Checks that the start page is HTTPS and that plain http:// redirects to HTTPS.

    Fix Enforce HTTPS and redirect http:// to https:// with a 301.

  • Permissions-Policy and Cross-Origin-Opener-Policy are set

    SEC-HDR-004 · Art. 32 GDPR

    How it is checked Reads the response headers of the start page for Permissions-Policy and a Cross-Origin-Opener-Policy other than unsafe-none, and names both when they appear only in <meta>, where browsers ignore them, or COOP only as report-only.

    Fix Set Permissions-Policy in the web server and turn off features the site does not use (for example camera=(), microphone=(), geolocation=()), plus Cross-Origin-Opener-Policy: same-origin, or same-origin-allow-popups when the site opens login or payment windows.

  • No unencrypted resources on HTTPS pages

    SEC-TLS-003 · Art. 32 GDPR

    How it is checked Lists http:// requests made by pages of an HTTPS site.

    Fix Load every resource over https://.

  • security.txt names a contact for vulnerabilities

    SEC-CVD-002 · Technical, no single law

    How it is checked Requests /.well-known/security.txt (in data/probes.yml) and reads its Contact and Expires fields.

    Fix Publish /.well-known/security.txt with Contact: (email or URL) and Expires: (at most a year ahead), and renew it before it expires.

  • Scripts and stylesheets from other sites carry an integrity hash

    SEC-HDR-003 · Art. 32 GDPR

    How it is checked Lists <script src> and <link rel=stylesheet> elements in the HTML of the site's own pages (load without JavaScript) that point to another site and have no integrity attribute, and leaves out services whose files change under the same URL (data/subresource-integrity.yml).

    Fix Load fixed versions of other sites' files with integrity="sha384-…" and crossorigin="anonymous" (most CDNs show the hash), or host the file yourself.

  • TLS certificate is valid and current

    SEC-TLS-002 · Art. 32 GDPR

    How it is checked Opens a TLS connection to the host and reads protocol, trust and expiry date of the certificate, warning 14 days before expiry (data/thresholds.yml).

    Fix Renew the certificate automatically (for example Let's Encrypt) and allow only TLS 1.2 and 1.3.

What a finding looks like

Each finding names the rule, the law it relates to, what was found and how to fix it.

Run it in CI

  1. Copy the example workflow to .github/workflows/rechtzeitig.yml. It pins a release by its commit SHA.
  2. Set url. To run only these checks, also set modules in the rechtzeitig step:
url: https://www.example.de/
modules: security
fail-on: fail # red when a check fails

The example runs every Monday, which catches an expiring certificate or a header lost in a deploy, see Run on a schedule.

All inputs, fail-on and the Security tab upload are described in The workflow. Findings are technical hints with the law they relate to, not legal advice.
