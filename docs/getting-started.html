Get started

From an empty repository to a first report in about ten minutes. Nothing about your project leaves the runner unless you turn it on.

On this page

  1. Add the workflow
  2. Say what to scan
  3. Decide what may leave the runner
  4. Start the first run
  5. Keep it running

§ 1Add the workflow

Copy the example workflow to .github/workflows/rechtzeitig.yml in your repository. It pins a release by its commit SHA, checks out the repository without keeping the token (persist-credentials: false) and needs no secret.

Never run it on pull_request_target. See Safe use.

§ 2Say what to scan

Set these in the with: block. Everything else can stay as it is.

InputSet it to
urlYour start page, for example https://www.example.de/. Leave it out to scan only the repository.
languageLanguage of the site: de, en or de,en.
salestrue if consumers buy or sign contracts on the site.
subscriptionstrue if visitors can sign up for subscriptions.

All inputs: Inputs.

Staging, preview and internal sites

Private or local hosts are allowed for the url host only; third parties and redirects on private addresses stay blocked. Three setups:

  • Preview URL (Vercel, Netlify): take it from a previous step's output. 
    - uses: kreativ-anders/rechtzeitig@…
  with:
    url: ${{ steps.deploy.outputs.preview-url }}
  • App started in the same job: the input host may be localhost. 
    - run: |
    npm start &
    sleep 5
- uses: kreativ-anders/rechtzeitig@…
  with:
    url: http://localhost:3000/
  • Intranet: use a self-hosted runner that can reach it. Only the url host is contacted, nothing else on the private network. 
    jobs:
  scan:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v6
      - uses: kreativ-anders/rechtzeitig@…
        with:
          url: https://intranet.example.de/

§ 3Decide what may leave the runner

Your source code never leaves the runner. The scan talks to your website and to GitHub. Lookups at other services are off until you turn them on, so the default run sends nothing about your project to a third party. Each one runs a check that is skipped without it.

Turn on withSendsToRuns
vulnerabilities: "true"Name and version of every locked component, internal packages includedapi.osv.devKnown vulnerabilities and the vulnerabilities in the SBOM

The vulnerability lookup is the one most projects want. If your security team reviews outside connections, show them this table and Data that leaves the runner, which also lists what the setup downloads.

§ 4Start the first run

Commit the file, then open Actions → rechtzeitig → Run workflow. A run with a website takes a few minutes.

  • Private repository: the full report is on the run page, and in the artifact rechtzeitig-report.
  • Public repository: the run page shows only counts; the findings go to the Security tab, which only people with write access see.

The first run is often red. Set fail-on: never until the findings are fixed. More: The report, fail-on.

§ 5Keep it running

The example runs every Monday, so a new tracker, an expiring certificate or a newly published vulnerability shows up a week later at most. Set fail-on: fail once the first findings are fixed. Add Dependabot for github-actions to get each new release as a pull request, see Updates.

Findings are technical risk hints with location and legal basis, not legal advice.
