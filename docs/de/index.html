Farbschema

Rechts- und Sicherheitslücken in schnell oder mit KI gebautem Code finden

rechtzeitig ist ein Vibe-Code-Check für jedes Webprojekt, ob von Hand oder mit KI gebaut: eine GitHub Action, die Ihr Repository und Ihre Live-Website auf deutsches und EU-Recht (DSGVO, Impressum, Cookie-Einwilligung) und Sicherheitsgrundlagen wie geleakte Keys, Security-Header und verwundbare Pakete prüft. Jeder Befund nennt die Stelle und das Gesetz.

Workflow kopieren Alle 94 Prüfungen ansehen

Kostenlos und Open Source (Apache-2.0), gepflegt von Manuel Steinberg, kreativ-anders, Deutschland. Kein Konto; der Code bleibt auf Ihrem Runner.

geprüftrechtzeitig

In einem Schritt einbauen

  1. rechtzeitig.yml nach .github/workflows/ im eigenen Repository kopieren.
  2. Darin die Startseite eintragen. Ohne url wird nur das Repository geprüft. 
    - uses: kreativ-anders/rechtzeitig@…
  with:
    url: https://www.example.de/
  3. Committen. Der Workflow läuft jeden Montag; den ersten Lauf unter Actions → rechtzeitig → Run workflow starten. Befunde stehen in der Zusammenfassung des Laufs und im Security-Tab, und GitHub schreibt Ihnen, wenn eine Prüfung fehlschlägt.

Alle Optionen: Konfiguration (Englisch).

Was geprüft wird

Repository und Website zusammen 13 Prüfungen

Was ein Scan nur einer Seite nicht sehen kann: der Code, der live geht, verglichen mit dem, was die Website tatsächlich ausliefert und erklärt.

  • Die Datenbank, die die Website nutzt, ist im Repository abgesichert
  • Keine Geheimnisse im ausgelieferten JavaScript
  • Impressum und Datenschutzerklärung ohne Vorlagendaten
  • Tracking-IDs aus dem Code laden nicht vor der Einwilligung
  • Consent-Tool aus dem Repository ist auf der Website aktiv
  • Keine Entwicklungs- oder Debug-Builds in Produktion
  • Datenschutzerklärung nennt die Dienste aus dem Code
  • Datenschutzerklärung nennt den Hoster
  • Datenschutzerklärung nennt die Empfänger der Formulare
  • Google Fonts: Herkunft im Repository gefunden
  • Source Maps legen den Code des Repositorys nicht offen
  • Sicherheits-Header aus dem Repository kommen auf der Website an
  • Die security.txt aus dem Repository ist live

  • Repository 31 Prüfungen

    Eingecheckte Schlüssel, bekannte Schwachstellen, Lizenzrisiken, riskante Workflows und KI-Agent-Einstellungen, unsichere Abkürzungen im Code. Dazu eine CycloneDX-SBOM.

  • Website 50 Prüfungen

    Impressum, Datenschutzerklärung, Cookies vor der Einwilligung, Security-Header und TLS, Grundlagen der Barrierefreiheit, Kündigungsbutton. Läuft, wenn Sie eine url angeben.

Quellen statt Rechtsberatung

Jede Prüfung nennt ihre Rechtsgrundlage und verlinkt Primärquellen: Gesetze, Gerichte, Behörden. Der Maintainer, Entwickler und kein Jurist, gleicht jede Regel mit diesen Quellen ab; Befunde sind Risikohinweise, keine Rechtsberatung.

Alle 94 Prüfungen wurden zuletzt zwischen dem 3. November 2026 und dem 11. November 2026 mit ihren Quellen abgeglichen. Eine Prüfung, die ein Jahr lang nicht abgeglichen wurde, lässt die Tests des Projekts scheitern.

Fragen

Wie bekomme ich die neueste Version?

Der Workflow pinnt ein Release über seinen Commit-SHA. Mit .github/dependabot.yml im Repository öffnet Dependabot für jedes neue Release einen Pull Request:

version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
Welches Recht wird geprüft?

Deutsches und EU-Recht: DSGVO, Impressum und Cookies (DDG, TDDDG), Verbraucherregeln für Shops (BGB), Barrierefreiheit (BFSG) und der Cyber Resilience Act. Die Sicherheits-, Lizenz- und Code-Prüfungen passen zu jedem Projekt. Berichte gibt es auf Deutsch oder Englisch. Läuft auf GitHub Actions; GitHub Enterprise Server ist nicht getestet.

Werde ich mit Warnungen zugeschüttet?

Jeder Befund ist fail für eine klare Lücke, warn für eine wahrscheinliche oder info für etwas zum Ansehen. Prüfungen, die nicht passen, etwa Shop-Regeln auf einer Website ohne Shop, werden übersprungen und sagen warum. Der Beispiel-Workflow lässt den Lauf nur bei fail scheitern (fail-on).

Verlassen Daten den Runner?

Der Quellcode nicht. Standardmäßig gehen Paketnamen und Versionen an osv.dev und der Hostname an die Green Web Foundation; beides lässt sich abschalten. Siehe Daten, die den Runner verlassen.

Wer kann den Bericht sehen?

In einem öffentlichen Repository zeigt die Seite des Laufs nur die Zahlen. Die Befunde gehen in den Security-Tab, den nur Personen mit Schreibrechten sehen. Siehe Der Bericht.

Befunde sind technische Risikohinweise mit Fundstelle und Rechtsgrundlage, keine Rechtsberatung.
