Impressum, Cookie-Einwilligung und Sicherheit prüfen, als GitHub Action

rechtzeitig ist ein DSGVO-Check als GitHub Action: Die Action prüft Website und Repository auf deutsche und EU-rechtliche Grundlagen, Security-Header, TLS und Lizenzen und schreibt eine CycloneDX-SBOM. Heraus kommt eine Liste von Stellen zum Beheben, jede mit dem Gesetz, auf das sie sich bezieht.

Kostenlos und Open Source. Kein Konto, kein Secret, der Code bleibt auf dem Runner.

Was geprüft wird

Wie eine DSGVO-Checkliste für Webentwickler, nur arbeitet sie der Workflow ab: Jeder Punkt ist eine Prüfung mit fester ID, Fundstelle und Rechtsgrundlage. Der Impressum-Checker und alle anderen Prüfungen sind Open Source.

  • Rechtstexte

    Das Impressum nach § 5 DDG und die Datenschutzerklärung nach DSGVO: verlinkt, erreichbar, vollständig

  • Cookie-Einwilligung

    Tracking und Cookies vor der Einwilligung nach § 25 TDDDG, Google Fonts und andere fremde Server, das Banner, Übermittlungen außerhalb der EU

  • Shop- und Vertragsbuttons

    Kündigungsbutton nach § 312k BGB, Widerrufsbutton, „zahlungspflichtig bestellen“ und Preise mit Grundpreis nach PAngV

  • Security-Header und TLS

    Security-Header-Check automatisch bei jedem Lauf: HTTPS, Zertifikate, offene .env- und .git-Dateien, Fehlerseiten, SPF und DMARC

  • Repository und SBOM

    CycloneDX-SBOM, bekannte Schwachstellen aus osv.dev, Lizenzkonflikte, Geheimnisse im Code wie API-Keys unter öffentlichen Präfixen, die ins Frontend-Bundle gelangen, Supabase-Tabellen ohne Row Level Security, Workflow-Risiken

  • Nachhaltigkeit und Barrierefreiheit

    Kompression, Caching, Bildformate, grünes Hosting, Seitensprache, Autoplay

So sieht ein Bericht aus

Der Bericht steht auf der Zusammenfassung des Laufs. Jede Zeile nennt die Prüfung, ihre Regel-ID, das Gesetz, auf das sie sich bezieht, und den Befund; eine Warnung kommt mit einem Hinweis zur Behebung.

In zwei Minuten starten

  1. rechtzeitig.yml nach .github/workflows/rechtzeitig.yml im eigenen Repository kopieren.
  2. Actions → rechtzeitig → Run workflow öffnen, URL eintragen und die Sprache wählen.
  3. Den Bericht auf der Zusammenfassung des Laufs lesen.

Das Beispiel startet von Hand. Für einen Lauf jede Woche oder bei jedem Push einen Trigger ergänzen: Zeitplan einrichten. Inputs, Secrets und Berichtsdateien: Der Workflow (Englisch).

Wer dahintersteht

rechtzeitig wird von Manuel Steinberg (kreativ-anders) in Deutschland entwickelt und gepflegt, als Open Source unter Apache-2.0. Jedes Release nennt, was sich geändert hat.

Alle 56 Prüfungen wurden zuletzt zwischen dem 3. November 2026 und dem 4. November 2026 mit ihren Quellen abgeglichen. Eine Prüfung, die ein Jahr lang nicht abgeglichen wurde, lässt die Tests des Projekts scheitern.

Fragen

Wie bekomme ich die neueste Version?

Der Workflow pinnt ein Release über seinen Commit-SHA. Dafür .github/dependabot.yml ins Repository legen:

version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly

Dependabot öffnet dann bei jedem neuen rechtzeitig-Release einen Pull Request. Nach dem Merge läuft die neue Version.

Läuft es auch nach Zeitplan oder bei jedem Push?

Ja. Der Beispiel-Workflow startet von Hand, rechtzeitig funktioniert aber mit jedem Trigger außer pull_request_target. Ein geplanter Lauf hat kein Formular, deshalb steht die URL in der Workflow-Datei: Zeitplan einrichten.

Ist das Rechtsberatung?

Nein. Ein Befund ist ein technischer Hinweis mit Fundstelle und dem Gesetz, auf das er sich bezieht, damit klar ist, wo zuerst hinzusehen ist. Ein Bericht ohne Befunde heißt, dass diese Prüfungen nichts gefunden haben, nicht, dass die Website rechtskonform ist.

Verlassen Daten den Runner?

Der Quellcode nicht. Standardmäßig gehen Namen und Versionen der Pakete aus den Lockfiles an osv.dev (vulnerabilities: false schaltet das ab) und der Hostname an die Green Web Foundation (green-hosting: false). Die vollständige Liste: Daten, die den Runner verlassen.

Wer kann den Bericht sehen?

In einem öffentlichen Repository standardmäßig nur die Zahlen, weil die Seite des Laufs öffentlich ist. Für den vollständigen Bericht rechtzeitig aus einem privaten Repository starten. Siehe Der Bericht.

Wie bleiben die Prüfungen aktuell?

Jede Prüfung nennt Primärquellen: Gesetze, Gerichte, Behörden oder Standards, keine Blogs. Jede hält fest, wann ihre Quellen zuletzt abgeglichen wurden. Eine Prüfung, die ein Jahr lang nicht abgeglichen wurde, lässt die Tests des Projekts scheitern und kann so nicht veröffentlicht werden. Die Releases nennen, was sich geändert hat.

Befunde sind technische Risikohinweise mit Fundstelle und Rechtsgrundlage, keine Rechtsberatung.
