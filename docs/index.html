Find the legal and security pitfalls that slip into AI-written code

More code is written with AI, and the same things keep slipping through: no imprint, trackers that load before consent, API keys in the repository, missing security headers, outdated packages. rechtzeitig is a GitHub Action that checks your repository and, if you give it a URL, your live website. You get a list of places to fix, most with the law they relate to.

Free and open source. It runs in your own CI, needs no account and no secret, and your code stays on the runner.

How it works

  • Repository and live site

    The repository holds what visitors never see: lockfiles, workflows, keys, database rules. The website shows what they get: HTML, scripts, cookies, headers, TLS and DNS. rechtzeitig checks both in one run and one report. Checks that compare the two directly are planned.

  • Every week, not once

    Run it on a schedule or on every push. A tracker that came with a new embed, a certificate close to expiry or a new vulnerability in a package you use shows up in the next run. See Run on a schedule.

  • Findings stay private

    On a private repository the run page shows the full report. On a public one it shows only counts by default, because anyone can open the run page. The findings go to the Security tab, which only people with write access see, where GitHub allows the upload.

  • A hint, not a verdict

    Each finding names the place and the rule, which cites its legal basis where there is one and links a primary source, so you know where to look first. It is a technical risk hint, not legal advice.

Typical pitfalls it checks

These are the gaps that come up again and again in sites built fast, by hand or with AI.

  • Legal pages

    The German imprint (Impressum) under § 5 DDG and the privacy policy under the GDPR: linked, reachable, complete

  • Cookie consent

    Third-party requests and cookies before consent, the banner, transfers outside the EU, § 25 TDDDG

  • Shop and contract buttons

    Cancellation, withdrawal and order buttons under the BGB, and prices under the PAngV. In German: Kündigungsbutton prüfen

  • Security headers and TLS

    HTTPS, certificates, headers, exposed .env and .git files, error pages, SPF and DMARC

  • Repository and SBOM

    Committed secrets, also under public prefixes such as NEXT_PUBLIC_ that end up in the browser bundle, Supabase tables without row level security, known vulnerabilities from osv.dev, license conflicts, workflow risks and a CycloneDX SBOM

  • Sustainability and accessibility

    Compression, caching, image formats, green hosting, page language, autoplay

What a report looks like

The report appears on the run's summary page. Each row names the check, its rule id, the law it relates to and what was found. A warning also says how to fix it.

Start in two minutes

  1. Copy rechtzeitig.yml to .github/workflows/rechtzeitig.yml in your repository.
  2. Set url and the language in the file.
  3. Wait for Monday or open Actions → rechtzeitig → Run workflow, then read the report on the run's summary page.

The example runs every week and fails when a check fails, so GitHub notifies you, see Run on a schedule. Inputs, secrets and report files are described in The workflow.

Questions

How do I get the latest version?

The workflow pins a release by its commit SHA. Add .github/dependabot.yml to your repository:

version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly

Dependabot then opens a pull request whenever a new rechtzeitig release is out. Merge it and you have the new version.

Can it run on a schedule or on every push?

Yes. The example workflow runs every Monday and can also be started by hand. rechtzeitig works with any trigger except pull_request_target; the URL goes into the workflow file: Run on a schedule.

Is this legal advice?

No. A finding is a technical hint with the place and the law it relates to, so you know where to look first. A clean report means these checks found nothing, not that the site is compliant.

Does any data leave the runner?

Your source code does not. By default the names and versions of your locked packages go to osv.dev (vulnerabilities: false turns it off) and your host name to the Green Web Foundation (green-hosting: false). The full list is under Data that leaves the runner.

Who can see the report?

On a public repository the run page shows only counts by default, because anyone can read it; the findings go to the Security tab, which only people with write access see. For the full report on the run page, run rechtzeitig from a private repository, or set report-visibility: full to publish it. More in The report.

How are the checks kept current?

Every check cites primary sources: laws, courts, authorities or standards, never blogs. Each records when its sources were last reviewed, and a check not reviewed for a year fails the project's tests, so it cannot be released. The releases list what changed.

Findings are technical risk hints with location and legal basis, not legal advice.
