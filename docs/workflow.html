§ 1Inputs

Every input is optional. An input you leave out, or set to an empty value, uses its default. This also holds for ${{ inputs.x }} on a scheduled run, where it is empty. The example workflow sets url, language, sales, subscriptions and fail-on, and lists the rest with their defaults, see Run on a schedule.

languagedeLanguage of the site: de, en, both as de,en, or all. Decides which words count as "Impressum", "Datenschutz" and so on.
subscriptionsfalsetrue if visitors can sign up for subscriptions. Turns on the cancellation button check (§ 312k BGB).
salesfalsetrue if consumers buy or sign contracts on the site. Turns on the shop checks: withdrawal, order button, prices and T&C link. To check a product or checkout page, point url at it.

Repository checkout

The repository checks read what actions/checkout leaves in the folder. By default that is the current commit without submodules and with Git LFS pointers instead of LFS files. To scan those too:

- uses: actions/checkout@<sha>
  with:
    persist-credentials: false
    submodules: recursive # files of submodules
    lfs: true             # LFS files instead of pointers
    # token: ${{ secrets.SUBMODULES_TOKEN }} # only for private submodules

The default GITHUB_TOKEN reads only this repository. Private submodules need a token with contents: read on them, for example a fine-grained personal access token or a GitHub App token, stored as a secret. Keep persist-credentials: false, so the token is not left in the checkout.

Only the checked-out files are read, never the git history: a secret that was removed in an earlier commit is not found. Files over 1 MB (lockfiles over 50 MB) and binary files are not read, and lockfiles of some ecosystems have no parser yet. The summary lists all of this under Scan, the JSON under coverage.

§ 5The report

report-visibility decides how much the run shows:

ValueShows
autoEverything for private and internal repositories. For public ones only how many checks ended in each status, with no details, annotations or artifact; the details go to the Security tab where GitHub allows the upload. A run whose event does not say counts as public.
fullSummary with findings, log, annotations and the artifact, also on a public repository, where anyone can read them. For deliberate transparency.

The values counts and none and the input retention-days were removed. counts and none work like auto for one more version and print a warning. GitHub warns about retention-days as an unexpected input, the run goes on.

The summary shows all findings, a collapsed list of the checks that did not run with how to turn them on, and under Scan what the repository scan could not read (see Repository checkout). Passed checks are only in the artifact. Findings in a repository file also show as annotations (GitHub shows at most 10 errors and 10 warnings). The artifact rechtzeitig-report contains:

FileContent
rechtzeitig-report.mdThe same report as Markdown
rechtzeitig-report.jsonFindings with rule id, severity, status, message, locations and, for skips, because; coverage lists what the repository scan could not read. No page text or file contents
rechtzeitig-sbom.cdx.jsonSBOM in CycloneDX 1.6 format, with vulnerabilities. Keep it with each release

On a public repository the run page is public, so auto shows only counts there. With full, anyone can read the findings and download the artifact (secret values are redacted, their file and line are not). GitHub deletes the artifact after 7 days, the log after 90 days by default. To keep the report private, run rechtzeitig from a private repository; a website-only scan needs no checkout.

Security tab

By default (sarif-upload: auto), findings also show as code scanning alerts in the repository's Security tab, which only people with write access see, even on a public repository. Website findings point to the workflow file and name the page. Each finding keeps its alert from run to run: a weekly run updates the alerts and closes fixed ones instead of adding new ones. The job needs:

permissions:
  contents: read
  security-events: write
  actions: read # private repositories only

Before the scan, rechtzeitig asks GitHub once whether code scanning is available. It skips the upload with a notice when:

  • the repository is private or internal without GitHub Code Security (a paid license for organizations on GitHub Team or Enterprise). On GitHub Free and Pro, private repositories have no code scanning at all.
  • the run is a pull request from a fork or was started by Dependabot. Their token is read-only.
  • the job lacks security-events: write.

Public repositories have code scanning for free. The upload never fails the job: with auto a skip or a failed upload is a notice, with true a warning. false writes no SARIF file and asks GitHub nothing.

GitHub Enterprise Server is not tested; it may work where a site admin has turned on code scanning. Treat it as best effort.

§ 6How the website is visited

Each page loads in a fresh Chromium, once without and once with JavaScript. Nothing is clicked and no consent is given, so every request and cookie in the report happened before consent. rechtzeitig opens the start page, the legal pages, a sample of other pages, and paths that must not be public (/.env, /.git/config, backups).

GitHub's runners are in the US, so a banner shown only to EU visitors will be missing. Pages behind a login are not checked.

§ 8Safe use

Never run rechtzeitig on pull_request_target: it gives code from a fork your secrets and a write token. Use workflow_dispatch, schedule, push or pull_request.

Check out with persist-credentials: false; rechtzeitig needs no token.

The scanned site is untrusted, so Chrome runs with its sandbox. On GitHub-hosted Ubuntu runners the action allows it with an AppArmor profile for the Chrome binary only; self-hosted runners are not changed. Without a sandbox the scan stops; require-sandbox: false scans anyway, only for sites you trust. No request reaches private addresses (localhost, 10.x, cloud metadata) except the host of url.

The action sets up Node 24, which stays on the PATH for later steps. Set up your own Node after it, or use a separate job.

§ 9Updates

The example workflow pins a release by its commit SHA. Dependabot moves the pin with a pull request for each new release, see How do I get the latest version? Without it, copy the uses: line from the latest release.

An update does not add new inputs to your workflow. Checks behind a switch stay off until you add it, see the release notes.

§ 10Questions

Run on a schedule or on push

The example workflow runs every Monday and has a Run workflow button without a form. Copy it and set url:

on:
  schedule:
    - cron: "17 5 * * 1" # Mondays, 05:17 UTC
  workflow_dispatch:
url: https://www.example.de/
language: de
sales: false
subscriptions: false
fail-on: fail # red when a check fails

With fail-on: fail, a run with a failing check turns red, and GitHub notifies the person who last changed the cron line. Runs stay red while a check fails, so the first run often is; until the findings are fixed, set fail-on: never if you prefer quiet runs. A minute other than :00 avoids the start of the hour, when GitHub delays scheduled runs. Scheduled runs use the default branch only. In a public repository, GitHub turns the schedule off after 60 days without activity in the repository.

To also run on each push, add push: branches: [main]. Limit it to the default branch: pushes by Dependabot get a read-only token. Never use pull_request_target, see Safe use.

Why does rechtzeitig not open issues?

Issues stay, notify people and are found by search engines, so on a public repository they would point everyone to a weakness of your site. They would also need issues: write. If you want one anyway, add a step after rechtzeitig that reads rechtzeitig-report.json and runs gh issue create, and give that step the permission.

A secret found in a public repository is already public. Revoke it first, then remove it from the code.

Findings are technical risk hints with location and legal basis, not legal advice.
